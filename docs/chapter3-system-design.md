## 3.1 ภาพรวมของระบบ

ระบบ NetMigrate ออกแบบเป็นสถาปัตยกรรมสามชั้น (Three-Tier Architecture) โดยแยก
ส่วนประมวลผลการแปลงไวยากรณ์ออกจากส่วนติดต่อผู้ใช้และส่วนจัดเก็บข้อมูลอย่างชัดเจน
การแยกชั้นเช่นนี้ทำให้กลไกการแปลงซึ่งเป็นแกนหลักทางวิชาการของโครงงาน สามารถทดสอบ
และประเมินผลได้โดยไม่ต้องอาศัยส่วนติดต่อผู้ใช้ และทำให้ผู้จัดทำทั้งสองคนพัฒนา
ไปพร้อมกันได้โดยลดการรอกันให้น้อยที่สุด

```
┌─────────────────────────────────────────────────────────┐
│  ชั้นนำเสนอ (Presentation Layer)                        │
│  Jinja2 Templates + Vanilla JavaScript (fetch)          │
│  หน้าแปลงไฟล์ · Diff View · คลังอุปกรณ์ · แดชบอร์ด      │
└──────────────────────┬──────────────────────────────────┘
                       │ HTTP / JSON
┌──────────────────────┴──────────────────────────────────┐
│  ชั้นประยุกต์ (Application Layer) — FastAPI             │
│  ┌───────────────────────────────────────────────────┐  │
│  │  กลไกการแปลง (Conversion Pipeline)                │  │
│  │                                                   │  │
│  │  Parser ──▶ IR ──▶ Renderer                       │  │
│  │              │                                    │  │
│  │              ├──▶ Rule Engine (กลไกหลัก)          │  │
│  │              └──▶ AI Fallback (เฉพาะที่ไม่มีกฎ)   │  │
│  └───────────────────────────────────────────────────┘  │
│  คิวแปลงไฟล์กลุ่ม · ตัวสร้าง Diff · ตัวเก็บค่าตัวชี้วัด │
└──────────────────────┬──────────────────────────────────┘
                       │
┌──────────────────────┴──────────────────────────────────┐
│  ชั้นจัดเก็บข้อมูล (Persistence Layer) — SQLite         │
│  conversions · conversion_lines · devices               │
└─────────────────────────────────────────────────────────┘
```

**จุดเชื่อมต่อระหว่างชั้น (API Contract)** กำหนดไว้ที่เมท็อด
`ConversionResult.to_dict()` ในโมดูล `netmigrate/ir.py` ชั้นนำเสนอเข้าถึงผลการแปลง
ผ่านโครงสร้าง JSON นี้เท่านั้น ไม่เข้าถึงโครงสร้างข้อมูลภายในโดยตรง เพื่อให้
แบบจำลองภายในสามารถปรับเปลี่ยนได้โดยไม่กระทบส่วนติดต่อผู้ใช้

## 3.2 การวิเคราะห์ความแตกต่างของไวยากรณ์ และการจัดประเภทกฎการแปลง

ขั้นตอนแรกของการออกแบบคือการวิเคราะห์ว่าความแตกต่างของไวยากรณ์ระหว่าง Cisco
IOS-XE และ Huawei VRP มีลักษณะอย่างไร ผลการวิเคราะห์นำไปสู่การจัดประเภทกฎการแปลง
ออกเป็นสามประเภท ซึ่งเป็น**ตัวกำหนดสถาปัตยกรรมของระบบทั้งหมด**

### 3.2.1 กฎประเภท Direct (D)

การแทนที่คำหรือบรรทัดแบบหนึ่งต่อหนึ่ง ความหมายและโครงสร้างไม่เปลี่ยน

| Cisco IOS-XE | Huawei VRP |
|---|---|
| `hostname SW1` | `sysname SW1` |
| `switchport mode access` | `port link-type access` |
| `switchport access vlan 10` | `port default vlan 10` |
| `no shutdown` | `undo shutdown` |
| `exit` / `end` | `quit` / `return` |

คิดเป็น 9 รายการจากชุดกฎทั้งหมด 16 รายการ (ร้อยละ 56)

### 3.2.2 กฎประเภท Transform (T)

หนึ่งบรรทัดต่อหนึ่งบรรทัด แต่ต้องแปลงรูปแบบของอาร์กิวเมนต์

**ตัวอย่างที่ 1 — รูปแบบรายการ VLAN**

```
Cisco:  switchport trunk allowed vlan 10,20,30-35
Huawei: port trunk allow-pass vlan 10 20 30 to 35
```

Cisco ใช้เครื่องหมายจุลภาคคั่นและขีดกลางแทนช่วง ขณะที่ VRP ใช้การเว้นวรรคและ
คำสำคัญ `to` การแปลงจำเป็นต้องแยกวิเคราะห์รายการให้เป็นเซตของหมายเลข VLAN แล้ว
สร้างขึ้นใหม่ตามรูปแบบของผู้ผลิตปลายทาง จึงออกแบบเป็นฟังก์ชันอิสระ
`parse_vlan_list_*()` และ `render_vlan_list_*()` ในโมดูล `transforms.py`

**ตัวอย่างที่ 2 — ค่าลำดับความสำคัญของเส้นทางคงที่**

```
Cisco:  ip route 10.0.0.0 255.0.0.0 192.168.1.1 200
Huawei: ip route-static 10.0.0.0 255.0.0.0 192.168.1.1 preference 200
```

Cisco รับค่า Administrative Distance เป็นจำนวนเต็มต่อท้ายโดยไม่มีคำสำคัญ ขณะที่
เอกสารอ้างอิงคำสั่งของ VRP กำหนดรูปแบบเป็น `[ preference preference | tag tag ] *`
กล่าวคือต้องระบุคำสำคัญ `preference` ระบบจึงปฏิเสธจำนวนเต็มต่อท้ายเปล่าในทิศทาง
Huawei → Cisco เพราะไม่ใช่ไวยากรณ์ที่ถูกต้องของ VRP

คิดเป็น 3 รายการจากชุดกฎทั้งหมด 16 รายการ (ร้อยละ 19)

### 3.2.3 กฎประเภท Structural (S) — ข้อค้นพบหลักของโครงงาน

กฎประเภทนี้มีการเปลี่ยนแปลงโครงสร้างการซ้อนบล็อกหรือลำดับบรรทัด กรณีตัวอย่างที่
สำคัญที่สุดคือการแปลงโปรโตคอล OSPF

```
! Cisco IOS-XE
router ospf 1
 router-id 1.1.1.1
 network 10.0.0.0 0.0.0.255 area 0
 network 10.1.0.0 0.0.0.255 area 0
 network 172.16.0.0 0.0.0.255 area 1
```

```
# Huawei VRP
ospf 1 router-id 1.1.1.1
 area 0.0.0.0
  network 10.0.0.0 0.0.0.255
  network 10.1.0.0 0.0.0.255
 area 0.0.0.1
  network 172.16.0.0 0.0.0.255
```

การแปลงนี้มีการเปลี่ยนแปลงเกิดขึ้นพร้อมกันสามประการ

1. **คำสั่ง `router-id` เลื่อนตำแหน่งขึ้น** จากบรรทัดลูกไปอยู่บนบรรทัดประกาศ Process
2. **Area กลายเป็นบล็อกแม่** ทำให้ต้องจัดกลุ่มคำสั่ง `network` ใหม่ตาม Area
   ซึ่งหมายความว่าระบบไม่สามารถสร้างผลลัพธ์บรรทัดใดได้เลย จนกว่าจะอ่านบล็อก
   `router ospf` ทั้งบล็อกจนจบ
3. **หมายเลข Area เปลี่ยนรูปแบบการแสดง** จากจำนวนเต็มเป็นเลขฐานสิบแบบมีจุด
   (Cisco `area 1` ↔ Huawei `area 0.0.0.1` โดย `0.0.0.1` คือ Area 1 ไม่ใช่
   Area 1.0.0.0 เนื่องจากเป็นการแสดงจำนวนเต็ม 32 บิตในรูปแบบ IPv4)

**ข้อสรุปเชิงสถาปัตยกรรม:** สถาปัตยกรรมแบบแทนที่รายบรรทัด (Line-by-Line
Substitution) ซึ่งเป็นแนวทางที่เข้าใจได้ง่ายที่สุดในเบื้องต้น **ไม่สามารถแสดง
การแปลงประเภทนี้ได้** เนื่องจากข้อมูลที่จำเป็นต่อการสร้างบรรทัดผลลัพธ์กระจายอยู่
ในหลายบรรทัดของไฟล์ต้นทาง ข้อจำกัดนี้เป็นเหตุผลที่โครงงานต้องใช้โครงสร้างข้อมูลกลาง

โครงสร้างการซ้อนบล็อกดังกล่าวได้รับการยืนยันจากเอกสารตัวอย่างการกำหนดค่าของ
Huawei เอง (Typical OSPF Configuration) ซึ่งแสดงรูปแบบตรงกับที่ระบบสร้างขึ้น

คิดเป็น 4 รายการจากชุดกฎทั้งหมด 16 รายการ (ร้อยละ 25) สัดส่วนนี้สูงกว่าที่คาดไว้ตอนออกแบบ ซึ่งยิ่งสนับสนุนการตัดสินใจ ไม่ใช้สถาปัตยกรรมแบบแทนที่รายบรรทัด

## 3.3 การออกแบบตัวแยกวิเคราะห์บล็อก (Block-Aware Parser)

### 3.3.1 เหตุผลของการใช้โครงสร้างต้นไม้

ไฟล์กำหนดค่าอุปกรณ์เครือข่ายไม่ใช่รายการคำสั่งที่เป็นอิสระต่อกัน แต่เป็นเอกสาร
ที่มีลำดับชั้น ความหมายของแต่ละบรรทัดขึ้นอยู่กับบล็อกที่บรรทัดนั้นอยู่ภายใน
ตัวอย่างที่ชัดเจนคือคำสั่ง `description UPLINK` ซึ่งมีความหมายอย่างหนึ่งเมื่ออยู่
ภายในบล็อก Interface และมีความหมายอีกอย่างหนึ่งเมื่ออยู่ภายในบล็อก VLAN

การเก็บไฟล์เป็นรายการบรรทัดแบบแบน (Flat List) จะทำให้ข้อมูลบริบทนี้สูญหาย
ตัวแยกวิเคราะห์จึงสร้างโครงสร้างต้นไม้ (`ConfigBlock`) ที่แต่ละโนดเก็บคำสั่ง
หมายเลขบรรทัดต้นฉบับ ระดับการย่อหน้า และรายการโนดลูก

### 3.3.2 การกำหนดลำดับชั้น

ระบบใช้ระดับการย่อหน้า (Indentation) เป็นเกณฑ์หลักในการกำหนดลำดับชั้น เนื่องจาก
ผลลัพธ์ของคำสั่ง `show running-config` ของ IOS-XE และ `display
current-configuration` ของ VRP ใช้การย่อหน้าอย่างสม่ำเสมอ

ระบบยังรู้จักคำสั่งปิดบล็อกอย่างชัดเจน (`exit`, `quit`, `end`, `return`) โดยนำมา
ปรับสถานะของสแตกบริบทแต่ไม่สร้างโนด ทั้งนี้กำหนดให้**การย่อหน้ามีน้ำหนักสูงกว่า**
คำสั่งปิดบล็อก เพราะไฟล์กำหนดค่าจริงจำนวนมากละคำสั่งปิดบล็อกทิ้งไป

### 3.3.3 การจัดการบรรทัดว่างและบรรทัดหมายเหตุ

บรรทัดว่างและบรรทัดหมายเหตุ (`!` ของ Cisco และ `#` ของ Huawei) **ถูกนับจำนวน
แต่ไม่ถูกบรรจุในโครงสร้างต้นไม้** เหตุผลคือตัวสร้างไฟล์ผลลัพธ์ต้องสร้างเครื่องหมาย
หมายเหตุของผู้ผลิตปลายทางขึ้นใหม่ หากนำหมายเหตุของต้นทางส่งผ่านไป ผลลัพธ์จะใช้
เครื่องหมายผิดผู้ผลิต

จำนวนบรรทัดที่ไม่ใช่บรรทัดว่างและไม่ใช่บรรทัดหมายเหตุล้วน เรียกว่า
**บรรทัดที่มีนัยสำคัญ (Significant Line)** และใช้เป็นตัวส่วนในการคำนวณค่า
ความครอบคลุมของกฎในบทที่ 4

## 3.4 การออกแบบโครงสร้างข้อมูลกลาง (Intermediate Representation)

### 3.4.1 โครงสร้าง

```
DeviceConfig
├── hostname: str
├── vlans: [ Vlan { vlan_id, name } ]
├── interfaces: [ Interface {
│       if_type, if_number,
│       description, ip_address, subnet_mask,
│       admin_down: bool | None,
│       link_type: ACCESS | TRUNK | None,
│       access_vlan, trunk_allowed: Set[int], trunk_native
│     } ]
├── static_routes: [ StaticRoute { prefix, mask, next_hop, preference } ]
├── ospf: OspfProcess {
│       process_id, router_id,
│       areas: { area_id -> [ Network { address, wildcard } ] }
│     } | None
└── unmapped: [ UnmappedBlock {
        text, source_line, category, guidance, suggestion, rationale
      } ]
```

### 3.4.2 การตัดสินใจออกแบบที่สำคัญสามประการ

**(ก) `OspfProcess.areas` เป็นโครงสร้างแบบแมป ไม่ใช่รายการแบน**

การเก็บ Area เป็นคีย์ที่ชี้ไปยังรายการ Network ภายใต้ Area นั้น เป็นสิ่งที่ทำให้
การแปลงประเภท Structural ในหัวข้อ 3.2.3 สามารถแสดงออกได้ หากเก็บ Network เป็น
รายการแบนพร้อมสนาม `area` ต่อรายการ ตัวสร้างไฟล์ฝั่ง Huawei จะต้องจัดกลุ่มใหม่
เองทุกครั้ง ซึ่งเป็นการย้ายความซับซ้อนไปไว้ในที่ที่ผิด

**(ข) `Interface.admin_down` เป็นค่าสามสถานะ (Tri-State)**

ค่าที่เป็นไปได้คือ `True` (ปิดใช้งาน) `False` (เปิดใช้งาน) และ `None`
(ไฟล์ต้นทางไม่ได้ระบุ) การแยกสถานะที่สามออกมาเป็นสิ่งจำเป็น เพราะค่าเริ่มต้นของ
สถานะพอร์ตไม่ตรงกันระหว่างผู้ผลิตและระหว่างประเภทอุปกรณ์ กล่าวคือพอร์ต Switch
ของ Cisco มีค่าเริ่มต้นเป็นเปิดใช้งาน พอร์ต Router ของ Cisco มีค่าเริ่มต้นเป็น
ปิดใช้งาน ขณะที่พอร์ตของ Huawei มีค่าเริ่มต้นเป็นเปิดใช้งาน

เมื่อไฟล์ต้นทางไม่ระบุคำสั่ง ระบบจะ**ไม่ระบุในไฟล์ผลลัพธ์เช่นกัน** โดยไม่พยายาม
อนุมานเจตนาของผู้ตั้งค่า การอนุมานในกรณีนี้อาจเปลี่ยนสถานะพอร์ตจริงบนอุปกรณ์
ปลายทาง

**(ค) ทุกวัตถุเก็บหมายเลขบรรทัดต้นฉบับ (`source_line`)**

เพื่อให้สามารถระบุแหล่งที่มาของการแปลงในระดับรายบรรทัด (Per-Line Provenance)
ได้ตลอดกระบวนการ ตั้งแต่ไฟล์ต้นทางจนถึงหน้าจอ Diff View และตารางฐานข้อมูล

## 3.5 การออกแบบ Rule Engine

### 3.5.1 รูปแบบการกระจายงาน (Dispatch)

ตัวอ่านไฟล์ของแต่ละผู้ผลิตใช้ตารางกระจายงาน (Dispatch Table) ที่แมปคำสำคัญระดับ
นอกสุดไปยังฟังก์ชันจัดการ

| คำสำคัญ (Cisco) | คำสำคัญ (Huawei) | ฟังก์ชันจัดการ |
|---|---|---|
| `hostname` | `sysname` | กำหนดชื่ออุปกรณ์ |
| `vlan` | `vlan`, `vlan batch` | สร้างและตั้งชื่อ VLAN |
| `interface` | `interface` | กำหนดค่า Interface |
| `ip` | `ip` | เส้นทางคงที่ |
| `router` | `ospf` | โปรโตคอล OSPF |

ฟังก์ชันจัดการแต่ละตัวจะดึงข้อมูลที่ตนรู้จักออกจากบล็อก และส่งบรรทัดลูกที่ไม่รู้จัก
ไปยังรายการ `unmapped` แนวทางนี้ทำให้**ไม่มีบรรทัดใดสูญหายโดยไม่มีการบันทึก**
ซึ่งเป็นคุณสมบัติที่ทำให้ค่าความครอบคลุมของกฎเป็นการวัดที่มีความหมาย

### 3.5.2 ชุดกฎที่พัฒนา

ระบบมีรหัสกฎ (Rule ID) ทั้งสิ้น 16 รายการ ครอบคลุมคำสำคัญระดับนอกสุด 5 กลุ่ม
และประเภท Interface 7 ประเภท ทำงานได้ทั้งสองทิศทาง

รหัสกฎสองรายการปรากฏในตัวสร้างไฟล์เพียงฝั่งเดียว คือ `ospf.router-id`
ปรากฏเฉพาะฝั่ง Cisco และ `ospf.area` ปรากฏเฉพาะฝั่ง Huawei ความไม่สมมาตรนี้
**คือ**การแปลงประเภท Structural ที่อธิบายไว้ในหัวข้อ 3.2.3 กล่าวคือข้อมูลชิ้น
เดียวกันปรากฏในตำแหน่งโครงสร้างที่ต่างกันบนสองผู้ผลิต

รายละเอียดทั้งหมดพร้อมสถานะการตรวจสอบกับเอกสารผู้ผลิตปรากฏใน **ภาคผนวก ก**
ซึ่งสร้างขึ้นโดยอัตโนมัติจากแคตาล็อกกฎในโค้ด (`netmigrate/rule_catalog.py`)
ด้วยคำสั่ง `python tools/make_appendix.py` และมีชุดทดสอบ `tests/test_catalog.py`
กำกับไว้ว่ากฎที่ปรากฏในโค้ดต้องมีรายการในแคตาล็อกและกลับกัน ตารางในปริญญานิพนธ์
จึงไม่สามารถคลาดเคลื่อนจากระบบที่พัฒนาจริงได้

### 3.5.3 กรณีที่ระบบปฏิเสธการแปลงโดยเจตนา

การออกแบบเลือก**ยอมเสียค่าความครอบคลุม เพื่อไม่ให้ข้อมูลสูญหายโดยเงียบ** กรณี
ต่อไปนี้ถูกส่งไปยังรายการ `unmapped` โดยเจตนา ไม่ใช่ข้อบกพร่อง

| คำสั่ง | เหตุผล |
|---|---|
| `port trunk allow-pass vlan all` | ไม่สามารถแสดงเป็นรายการ VLAN ที่ระบุชัดเจนของ Cisco ในขอบเขตได้ |
| `port link-type hybrid` | ไม่มีคำสั่งเทียบเคียงใน Cisco ภายในขอบเขต |
| `ip route-static ... 150` (ไม่มีคำสำคัญ `preference`) | ไม่ใช่ไวยากรณ์ที่ถูกต้องของ VRP |
| `ip route ... name BACKUP` | หากแปลงจะทิ้งชื่อเส้นทางโดยไม่แจ้ง |
| `vlan 10,20` พร้อมคำสั่ง `name` | ชื่อเดียวไม่สามารถใช้กับ VLAN หลายรายการได้ |

## 3.6 การออกแบบตัวสร้างไฟล์ผลลัพธ์ (Renderer)

ตัวสร้างไฟล์แต่ละตัวรับ `DeviceConfig` และคืนรายการ `OutputLine` โดยแต่ละบรรทัด
บรรจุข้อความ แหล่งที่มา (`RULE` / `AI` / `UNMAPPED` / `GENERATED`) รหัสกฎที่สร้าง
บรรทัดนั้น หมายเลขบรรทัดต้นฉบับ และธงบ่งชี้ว่าต้องตรวจสอบด้วยมือหรือไม่

### 3.6.1 การจัดการขีดจำกัดของคำสั่งปลายทาง

เอกสารอ้างอิงคำสั่งของ Huawei ระบุรูปแบบคำสั่งอนุญาต VLAN บนพอร์ต Trunk ไว้เป็น

```
port trunk allow-pass vlan { { vlan-id1 [ to vlan-id2 ] } &<1-40> | all }
```

สัญลักษณ์ `&<1-40>` หมายถึงจำนวนองค์ประกอบสูงสุด 40 รายการต่อคำสั่งหนึ่งคำสั่ง
โดยที่**ช่วงหนึ่งช่วงนับเป็นหนึ่งองค์ประกอบ** ไม่ใช่นับตามจำนวน VLAN ระบบจึงแบ่ง
รายการ VLAN ที่มีองค์ประกอบเกิน 40 รายการออกเป็นหลายคำสั่ง ซึ่งทำได้อย่างปลอดภัย
เพราะคำสั่ง `allow-pass` ที่ปรากฏซ้ำจะสะสมค่ากันบนอุปกรณ์ และตัวอ่านไฟล์ฝั่ง
Huawei ของระบบก็สะสมค่าเช่นเดียวกัน

### 3.6.2 การจัดการหมายเลขพอร์ต

รูปแบบการนับหมายเลขพอร์ตสะท้อนโครงสร้างฮาร์ดแวร์ทางกายภาพ จึงไม่มีการแมปที่
ถูกต้องสมบูรณ์ด้วยอัลกอริทึม ระบบจึงแปลงเฉพาะส่วนที่เป็น**ประเภท**ของ Interface
และคงส่วนที่เป็น**ตัวเลข**ไว้ตามเดิม พร้อมสร้างข้อความแจ้งเตือนให้ตรวจสอบเมื่อ
หมายเลข Slot ไม่เป็นศูนย์ในรูปแบบที่มีเครื่องหมายทับ

ทั้งนี้ Interface เชิงตรรกะ (LoopBack, Vlanif, Eth-Trunk) ได้รับการยกเว้นจาก
การแจ้งเตือนนี้ เพราะหมายเลขของ Interface เหล่านั้นเป็นดัชนีหรือหมายเลข VLAN
ไม่ใช่หมายเลข Slot กล่าวคือ `Vlanif10` หมายถึง VLAN 10 ไม่ใช่ Slot 10

## 3.7 การออกแบบกลไกสำรองด้วยปัญญาประดิษฐ์ (AI Fallback)

### 3.7.1 เงื่อนไขการเรียกใช้

กลไกนี้ถูกเรียกใช้**เฉพาะกรณีที่ตัวอ่านไฟล์สร้างรายการ `UnmappedBlock` เท่านั้น**
ไม่ถูกเรียกใช้สำหรับคำสั่งที่ Rule Engine แปลงได้ เงื่อนไขนี้เป็นสิ่งที่ทำให้
ค่าความครอบคลุมของกฎในบทที่ 4 เป็นการวัดที่มีความหมาย หากกลไก AI ทำงานทุกครั้ง
ที่มีการตั้งค่า API Key ค่าดังกล่าวจะไม่ได้วัดสิ่งใด

### 3.7.2 ขอบเขตของผลลัพธ์

ผลลัพธ์จากแบบจำลองภาษาถูกบรรจุในสนาม `suggestion` และ `rationale` ของ
`UnmappedBlock` และตัวสร้างไฟล์จะแสดงผลในรูปของ**ข้อความหมายเหตุพร้อมป้ายให้
ตรวจสอบเท่านั้น** ระบบไม่มีเส้นทางการทำงานใดที่นำคำแนะนำจาก AI ไปเป็นคำสั่งใน
ไฟล์ผลลัพธ์โดยตรง คุณสมบัตินี้มีชุดทดสอบกำกับไว้โดยเฉพาะ
(`test_ai_output_never_uncommented`)

### 3.7.3 การกีดกันข้อมูลรหัสผ่านออกจากการส่งไปยังบริการภายนอก

บรรทัดที่บรรจุข้อมูลรหัสผ่าน**ถูกคัดออกก่อนการสร้างคำสั่งส่งไปยัง API** การส่ง
ค่าแฮชรหัสผ่านจากไฟล์กำหนดค่าขององค์กรไปยังบริการของบุคคลที่สาม เป็นความบกพร่อง
ด้านความปลอดภัยไม่ว่าคำแนะนำที่ได้รับกลับมาจะมีประโยชน์เพียงใด ระบบยังมีการตรวจสอบ
ชั้นที่สอง กล่าวคือหากคำแนะนำที่ได้รับกลับมาบรรจุข้อมูลที่มีลักษณะเป็นรหัสผ่าน
ระบบจะปฏิเสธคำแนะนำนั้น

### 3.7.4 การไม่ใช้ค่าความมั่นใจที่แบบจำลองรายงานเอง

ค่าความมั่นใจ (Confidence Score) ที่แบบจำลองรายงานถูกบันทึกและแสดงบนส่วนติดต่อ
ผู้ใช้ แต่**ถูกตัดออกจากตัวชี้วัดการประเมินผลทุกตัว** เหตุผลคือค่าดังกล่าวไม่ใช่
ตัวชี้วัดความน่าเชื่อถือที่ผ่านการตรวจสอบความสมเหตุสมผล ผลลัพธ์ที่อ่านลื่นไหล
ถูกต้องตามไวยากรณ์ และรายงานค่าความมั่นใจสูง อาจผิดพลาดในเชิงความหมายได้
และตัวแบบจำลองไม่มีสัญญาณภายในที่เชื่อถือได้ในการแยกแยะสองกรณีนี้

### 3.7.5 การทำงานเมื่อไม่มีกลไก AI

ระบบทำงานได้สมบูรณ์เมื่อไม่ได้ตั้งค่า API Key โดยบรรทัดที่ไม่มีกฎรองรับจะคงสถานะ
เป็น `UNMAPPED` พร้อมข้อความแจ้งเตือน คุณสมบัตินี้ทำให้การรันประเมินผลสามารถ
ทำซ้ำได้ (Reproducible) และทำให้ชุดทดสอบทั้งหมดรันได้โดยไม่ต้องเชื่อมต่อเครือข่าย

## 3.8 การจัดการคำสั่งที่ไม่สามารถแปลงได้

### 3.8.1 รูปแบบการแจ้งเตือน

คำสั่งที่ไม่มีกฎรองรับถูกบรรจุในไฟล์ผลลัพธ์เป็นข้อความหมายเหตุ โดยใช้เครื่องหมาย
หมายเหตุของ**ผู้ผลิตปลายทาง** พร้อมป้าย `[NETMIGRATE-REVIEW]` และหมายเลขบรรทัด
ต้นฉบับ

```
# [NETMIGRATE-REVIEW] source line 47: ip nbar protocol-discovery
```

### 3.8.2 ข้อมูลรหัสผ่าน — กรณีที่ไม่สามารถแปลงได้ในทางหลักการ

ไฟล์กำหนดค่าจัดเก็บรหัสผ่านในรูปของค่าแฮช โดยใช้อัลกอริทึมที่แตกต่างกันตาม
ผู้ผลิตและตามรุ่น เช่น Cisco Type 5 (Salted MD5) Type 8 (PBKDF2-SHA256)
Type 9 (scrypt) และ Huawei irreversible-cipher ซึ่งใช้กลไกของตนเอง

อัลกอริทึมเหล่านี้เป็นฟังก์ชันทางเดียว (One-Way Function) ที่มีอัลกอริทึม ค่าเกลือ
และรูปแบบการเข้ารหัสต่างกัน จึง**ไม่มีการแปลงจากรูปแบบหนึ่งไปสู่อีกรูปแบบหนึ่ง**
โดยไม่มีข้อความรหัสผ่านต้นฉบับ ซึ่งไฟล์กำหนดค่าไม่ได้บรรจุไว้

ระบบจึงตรวจจับบรรทัดที่บรรจุข้อมูลรหัสผ่าน และสร้างข้อความแนะนำโครงสร้างคำสั่ง
สำหรับการตั้งค่าด้วยมือแทนการพยายามแปลง

```
# [NETMIGRATE-REVIEW] source line 12: enable secret 5 $1$mERr$H2s...
#   Password hashes cannot be converted between vendors (one-way,
#   vendor-specific algorithms). Set credentials manually on the target:
#     aaa
#      local-user <NAME> password irreversible-cipher <PLAINTEXT>
#      local-user <NAME> privilege level 15
```

### 3.8.3 การแจ้งเตือนความแตกต่างของค่าเริ่มต้นเชิงความหมาย

นอกจากความแตกต่างเชิงไวยากรณ์ ระบบยังตรวจพบกรณีที่**ไวยากรณ์แปลงได้ถูกต้อง
แต่พฤติกรรมบนอุปกรณ์อาจไม่เท่าเดิม** กรณีที่พบคือค่าเริ่มต้นของลำดับความสำคัญ
ของเส้นทางคงที่

เอกสารของ Huawei ระบุว่าเส้นทางคงที่ที่ไม่ได้กำหนดค่า preference จะใช้ค่าเริ่มต้น
เท่ากับ 60 ขณะที่ค่า Administrative Distance เริ่มต้นของเส้นทางคงที่บน Cisco
เท่ากับ 1 ดังนั้นเส้นทางคงที่ที่ไม่ระบุค่าจะมีลำดับความสำคัญเมื่อเทียบกับโปรโตคอล
จัดเส้นทางแบบพลวัต**ไม่เท่ากันบนอุปกรณ์สองผู้ผลิต**

ระบบสร้างข้อความแจ้งเตือนหนึ่งครั้งต่อไฟล์ เมื่อพบเส้นทางคงที่ที่อาศัยค่าเริ่มต้น
ของผู้ผลิต การแจ้งเตือนครั้งเดียวต่อไฟล์ ไม่ใช่ต่อเส้นทาง เพื่อรักษาความอ่านง่าย
ของไฟล์ผลลัพธ์

## 3.9 การออกแบบฐานข้อมูล

```sql
conversions (
  id, created_at, source_vendor, target_vendor, filename,
  total_lines, significant_lines,
  rule_lines, ai_lines, unmapped_lines,
  duration_ms, source_text, output_text
)

conversion_lines (
  id, conversion_id, source_line_no, output_line_no,
  provenance,        -- RULE | AI | UNMAPPED | GENERATED
  rule_id, needs_review
)

devices (
  id, hostname, ip_address, vendor, os_version,
  ssh_port, location, status, notes
)
```

ตาราง `conversion_lines` มีอยู่เพื่อให้ค่าตัวชี้วัดในบทที่ 4 สามารถสืบค้นได้จาก
ฐานข้อมูลโดยตรง ไม่ต้องคำนวณใหม่ และเพื่อให้ระบบประวัติการทำงานสามารถสร้าง
หน้าจอเปรียบเทียบ Diff ของการแปลงครั้งก่อนขึ้นใหม่ได้

ระบบใช้ SQLite ซึ่งเป็นฐานข้อมูลถาวรแบบไฟล์เดียวและเป็นส่วนหนึ่งของ Standard
Library ของภาษา Python แทนการจัดเก็บในหน่วยความจำชั่วคราวตามที่ระบุไว้ในข้อเสนอ
โครงงานฉบับแรก เหตุผลคือประวัติการทำงานที่สูญหายเมื่อ Restart เซิร์ฟเวอร์
ไม่ถือเป็นประวัติที่ตรวจสอบย้อนหลังได้

ผลลัพธ์ที่ตรวจสอบแล้วว่าถูกต้องถูกบันทึกไว้เป็นไฟล์อ้างอิง การเปลี่ยนแปลงใดที่
ทำให้ผลลัพธ์ต่างจากไฟล์อ้างอิงจะทำให้ชุดทดสอบล้มเหลวทันที กลไกนี้ป้องกันไม่ให้
การพัฒนากฎใหม่ทำลายกฎที่พัฒนาไว้ก่อนหน้าโดยไม่รู้ตัว

**การตรวจสอบว่าชุดทดสอบสามารถล้มเหลวได้จริง** ผู้จัดทำได้ทดลองแก้ไขตัวสร้างไฟล์
ให้สะกดคำสั่ง `port link-type access` ผิดเป็น `acess` โดยเจตนา และยืนยันว่า
ชุดทดสอบตรวจจับได้และรายงานความแตกต่างที่ตำแหน่งถูกต้อง การทดสอบการถดถอยที่ยัง
ไม่เคยถูกตรวจสอบว่าล้มเหลวได้จริง ไม่ถือเป็นการทดสอบการถดถอย

### 3.10.3 การทดสอบการแปลงกลับ (Round-Trip Testing) — วัดที่ระดับ IR

ระบบแปลงไฟล์จากผู้ผลิต A ไป B แล้วแปลงกลับมาเป็น A และเปรียบเทียบผลลัพธ์กับ
ไฟล์ต้นฉบับ โดย**เปรียบเทียบที่ระดับโครงสร้างข้อมูลกลาง ไม่ใช่ที่ระดับข้อความ**

เหตุผล: การแปลงไปและกลับทำให้ข้อความเปลี่ยนแปลงโดยชอบ เครื่องหมายหมายเหตุต่างกัน
ตัวคั่นถูกสร้างขึ้นใหม่ และลำดับบล็อกเป็นการตัดสินใจของตัวสร้างไฟล์ ความแตกต่าง
เหล่านี้ไม่ใช่การสูญหายของข้อมูล การเปรียบเทียบที่ระดับข้อความจะรายงานว่าล้มเหลว
ในกรณีที่ไม่ได้ล้มเหลวจริง และทำให้ค่า H2 ต่ำกว่าความเป็นจริง

การเปรียบเทียบที่ระดับ IR ตั้งคำถามที่ตรงประเด็น คือ**เจตนาของการตั้งค่าใด
สูญหายหรือเปลี่ยนแปลงไปในระหว่างการแปลงไปและกลับหรือไม่**

สนามข้อมูลที่ถูกยกเว้นจากการเปรียบเทียบมีสองรายการ

1. `source_line` — หมายเลขบรรทัดเปลี่ยนแปลงโดยจำเป็น
2. `unmapped` — คำสั่งที่ไม่มีกฎรองรับคงอยู่ในรูปข้อความหมายเหตุ ซึ่งตัวอ่านไฟล์
   ไม่นำกลับเข้าสู่ IR การสูญหายส่วนนี้ถูกนับด้วยตัวชี้วัด `unmapped_lines`
   อยู่แล้ว การนับซ้ำในค่า H2 จะเป็นการลงโทษข้อจำกัดเดียวกันสองครั้ง

### 3.10.4 การทดสอบความคงที่ของผลลัพธ์ (Determinism)

ระบบแปลงไฟล์เดิมซ้ำหกครั้งและตรวจสอบว่าผลลัพธ์ตรงกันทุกไบต์ การทดสอบนี้จำเป็น
เพราะไฟล์อ้างอิงในหัวข้อ 3.10.2 จะไม่มีประโยชน์หากตัวสร้างไฟล์ให้ผลลัพธ์ไม่คงที่
เช่น ลำดับการวนซ้ำของ Set หรือ Dictionary รั่วไหลออกมาในผลลัพธ์

### 3.10.5 คุณสมบัติด้านความปลอดภัยที่มีชุดทดสอบกำกับ

| คุณสมบัติ | ชุดทดสอบ |
|---|---|
| ผลลัพธ์จาก AI ไม่ปรากฏนอกข้อความหมายเหตุ | `test_ai_output_never_uncommented` |
| ข้อมูลรหัสผ่านไม่ปรากฏนอกข้อความหมายเหตุ | `test_credential_never_appears_uncommented` |
| ข้อมูลรหัสผ่านไม่ถูกส่งไปยัง API ภายนอก | `test_credentials_are_never_sent` |
| กลไก AI ไม่เปลี่ยนค่าความครอบคลุมของกฎ | `test_coverage_unchanged_by_fallback` |

| เครื่องมือ | หน้าที่ |
|---|---|
| `tools/evaluate.py` | รันชุดข้อมูลทดสอบทั้งหมด เก็บค่าตัวชี้วัด ส่งออกเป็น CSV สำหรับบทที่ 4 |

| `tools/demo.py` | สาธิตการทำงานครบวงจรสำหรับการนำเสนอ |

ที่ถูกรบกวนด้วยการจัดสรรเวลาของระบบปฏิบัติการเป็นส่วนใหญ่ ค่าต่ำสุดและสูงสุด
ถูกบันทึกไว้ด้วยเพื่อให้เห็นการกระจายของข้อมูล

## 3.12 สรุปการเปลี่ยนแปลงจากข้อเสนอโครงงาน

| หัวข้อ | ข้อเสนอเดิม | ที่พัฒนาจริง | เหตุผล |
|---|---|---|---|
| การจัดเก็บข้อมูล | In-Memory | SQLite | ประวัติที่สูญหายเมื่อ Restart ไม่ใช่ประวัติที่ตรวจสอบย้อนหลังได้ |
| สภาพแวดล้อม | Node.js / Python | Python เท่านั้น | ลดความเสี่ยงจากการเชื่อมต่อสองสภาพแวดล้อมภายในเวลาที่จำกัด |
| เงื่อนไขเรียกใช้ AI | คลุมเครือสองเงื่อนไข | เฉพาะเมื่อไม่มีกฎรองรับ | เพื่อให้ค่าความครอบคลุมของกฎมีความหมาย |
| สถานะพอร์ต | ไม่ได้ระบุ | ค่าสามสถานะ | ค่าเริ่มต้นของผู้ผลิตไม่ตรงกัน การอนุมานจึงเป็นความเสี่ยง |
| ข้อมูลรหัสผ่าน | ไม่ได้ระบุ | ตรวจจับและแนะนำ ไม่แปลง | เป็นฟังก์ชันทางเดียว ไม่มีการแปลงในทางหลักการ |
| การรองรับสองภาษา | อยู่ในขอบเขต | ตัดออก | ใช้เวลาพัฒนาสูง ไม่สนับสนุนวัตถุประสงค์ของโครงงาน |
