## 2. รายละเอียดโครงงาน

### 2.1 ความเป็นมาและความสำคัญของปัญหา

ในยุคปัจจุบันที่โครงสร้างพื้นฐานทางดิจิทัลเป็นหัวใจสำคัญในการขับเคลื่อนองค์กร ระบบเครือข่าย
คอมพิวเตอร์จำเป็นต้องมีความยืดหยุ่น มีประสิทธิภาพสูง และรองรับการขยายตัวได้อย่างต่อเนื่อง
ส่งผลให้องค์กรส่วนใหญ่ปรับเปลี่ยนกลยุทธ์จากการใช้อุปกรณ์จากผู้ผลิตรายเดียว ไปสู่โครงสร้าง
แบบผสมผสานจากหลากหลายผู้ผลิต (Multi-Vendor) เช่น Cisco และ Huawei เพื่อลดความเสี่ยง
จากการพึ่งพาผู้ผลิตรายใดรายหนึ่ง เพิ่มอำนาจในการต่อรองราคา และสามารถเลือกใช้อุปกรณ์ที่มี
คุณสมบัติเหมาะสมกับความต้องการของระบบได้อย่างมีประสิทธิภาพสูงสุด ในบริบทของประเทศไทย
รูปแบบดังกล่าวปรากฏชัดในหน่วยงานภาคการศึกษา ภาครัฐ และผู้ให้บริการเครือข่าย ซึ่งจัดหาอุปกรณ์
ผ่านกระบวนการจัดซื้อจัดจ้างหลายปีงบประมาณและหลายสัญญา

อย่างไรก็ตาม โครงสร้างแบบ Multi-Vendor ก่อให้เกิดความซับซ้อนอย่างมากเมื่อต้องย้ายหรือ
ปรับเปลี่ยนระบบ เนื่องจากผู้ผลิตแต่ละรายมีรูปแบบภาษาและโครงสร้างคำสั่งการตั้งค่า
(Configuration Syntax) ที่เป็นเอกสิทธิ์เฉพาะตัว เช่น ความแตกต่างระหว่าง Cisco IOS-XE และ
Huawei VRP ทำให้ผู้ดูแลระบบต้องดำเนินการแปลงไฟล์ Configuration ด้วยตนเอง ซึ่งเป็น
กระบวนการที่ยุ่งยาก ซับซ้อน ต้องใช้วิศวกรเครือข่ายที่มีความเชี่ยวชาญสูง ทั้งยังใช้เวลานาน
และมีอัตราการเกิดข้อผิดพลาดจากมนุษย์สูง

ข้อผิดพลาดดังกล่าวมีผลกระทบรุนแรง ตัวอย่างเช่น การพิมพ์รายการ VLAN บนพอร์ต Trunk
ผิดพลาดเพียงค่าเดียว อาจทำให้เครือข่ายส่วนหนึ่งถูกตัดขาดจากระบบ หรือการประกาศ Area
ของโปรโตคอล OSPF ด้วยไวยากรณ์ที่ไม่ถูกต้อง อาจไม่แสดงอาการผิดปกติจนกระทั่งเส้นทาง
สำรองถูกเรียกใช้งาน และเนื่องจากการเปลี่ยนแปลงค่าอุปกรณ์มักดำเนินการในช่วงเวลาบำรุงรักษา
(Maintenance Window) ข้อผิดพลาดที่ตรวจพบล่าช้าจึงเป็นข้อผิดพลาดที่ต้องแก้ไขภายใต้
ข้อจำกัดด้านเวลาอย่างรุนแรง

การแปลงคำสั่งด้วยระบบอัตโนมัติจึงเป็นแนวทางที่น่าสนใจ แต่ยังไม่ใช่ปัญหาที่ได้รับการแก้ไข
อย่างสมบูรณ์ แนวทางมาตรฐานของอุตสาหกรรมในปัจจุบันคือการใช้แบบจำลองข้อมูลที่ไม่ขึ้นกับ
ผู้ผลิต (Vendor-Neutral Modelling) ได้แก่ NETCONF/YANG และ OpenConfig ซึ่งกำหนดให้
ตัวอุปกรณ์ต้องรองรับมาตรฐานดังกล่าวด้วยตนเอง แต่อุปกรณ์จำนวนมากที่ติดตั้งใช้งานอยู่แล้ว
(Installed Base) ไม่รองรับ และองค์กรมักมีความจำเป็นต้องย้ายไฟล์กำหนดค่าที่เป็นข้อความ
ธรรมดาจากอุปกรณ์เดิมเหล่านั้น ช่องว่างนี้คือประเด็นที่โครงงานนี้มุ่งแก้ไข

**ข้อความปัญหาของโครงงาน (Statement of the Problem)**

ยังไม่มีเครื่องมือที่เข้าถึงได้ทั่วไป ซึ่งสามารถแปลงไฟล์กำหนดค่าที่เป็นข้อความธรรมดาระหว่าง
Cisco IOS-XE และ Huawei VRP ได้แบบสองทิศทาง พร้อมกับระบุระดับความน่าเชื่อถือของ
การแปลงในแต่ละบรรทัดให้ผู้ตรวจสอบทราบอย่างชัดเจน ปัญหาย่อยมีสองประการ คือ

1. **ความครอบคลุม (Coverage)** — ระบบที่ใช้กฎ (Rule-Based) สามารถแปลงได้เฉพาะคำสั่ง
   ที่มีการเขียนกฎรองรับไว้ ไฟล์กำหนดค่าจริงมีคำสั่งเฉพาะของผู้ผลิตซึ่งอยู่นอกขอบเขตของ
   ชุดกฎที่ปฏิบัติได้ ระบบที่ละเว้นหรือแปลคำสั่งเหล่านี้ผิดพลาดโดยไม่แจ้งเตือนจึงไม่ปลอดภัย

2. **ความน่าเชื่อถือและการตรวจสอบย้อนหลัง (Trust and Auditability)** — การแปลงไฟล์
   กำหนดค่าที่จะนำไปใช้กับระบบจริงต้องสามารถตรวจสอบย้อนหลังได้ ผู้ดูแลระบบจำเป็นต้อง
   ทราบว่าบรรทัดใดแปลงด้วยกฎที่กำหนดผลลัพธ์แน่นอน (Deterministic) บรรทัดใดเกิดจาก
   วิธีการเชิงความน่าจะเป็น (Probabilistic) และบรรทัดใดไม่สามารถแปลงได้

### 2.2 วัตถุประสงค์ของการจัดทำโครงงานพิเศษ

2.2.1 เพื่อออกแบบและพัฒนาระบบแปลงไฟล์กำหนดค่าอุปกรณ์เครือข่ายแบบสองทิศทางระหว่าง
Cisco IOS-XE และ Huawei VRP ในชุดคำสั่งที่กำหนดขอบเขตไว้ โดยใช้กลไกการแปลงแบบกฎ
(Rule Engine) ที่ทำงานบนโครงสร้างข้อมูลกลางที่ไม่ขึ้นกับผู้ผลิต (Vendor-Neutral
Intermediate Representation)

2.2.2 เพื่อประยุกต์ใช้แบบจำลองภาษาขนาดใหญ่ (Large Language Model) เป็นกลไกสำรอง
ที่มีขอบเขตจำกัด ซึ่งทำหน้าที่ **เสนอคำแนะนำที่กำกับให้ตรวจสอบ** (Flagged Suggestion)
สำหรับคำสั่งที่อยู่นอกชุดกฎ โดยไม่นำผลลัพธ์ไปใช้โดยอัตโนมัติ และเพื่อวัดระดับความสอดคล้อง
ของคำแนะนำดังกล่าวกับผลการแปลที่ผ่านการตรวจสอบโดยผู้มีความรู้

2.2.3 เพื่อประเมินประสิทธิภาพของระบบด้วยชุดข้อมูลทดสอบ (Test Corpus) จำนวน 15–30 ไฟล์
ที่จัดทำขึ้นเฉพาะ โดยรายงานค่าความครอบคลุมของกฎ (Rule Coverage) ความคงเดิมของ
การแปลงกลับ (Round-Trip Fidelity) ความสำเร็จในการนำเข้าไฟล์ผลลัพธ์บนโปรแกรมจำลอง
อุปกรณ์ และระยะเวลาการแปลงเทียบกับเกณฑ์พื้นฐานที่วัดจากการทำด้วยตนเอง

> **หมายเหตุการแก้ไข:** วัตถุประสงค์ข้อ 2.2.2 เดิมระบุว่า "เพื่อลดระยะเวลาการทำงาน และลด
> อัตราการเกิดข้อผิดพลาดจากมนุษย์" ซึ่งเป็นการระบุ *ผลลัพธ์ที่คาดหวัง* มากกว่า *วัตถุประสงค์
> ของการดำเนินงาน* และไม่ได้ระบุวิธีวัด จึงย้ายไปไว้ในข้อ 2.9 ในรูปของสมมติฐานที่ทดสอบได้
> พร้อมนิยามการวัดในข้อ 2.6 การปรับเช่นนี้ทำให้วัตถุประสงค์ทุกข้อสามารถตรวจสอบได้ว่า
> บรรลุหรือไม่ ซึ่งเป็นประเด็นที่คณะกรรมการมักตั้งคำถาม

### 2.3 ขอบเขตของการทำโครงงานพิเศษ (Scope of Special Project)

#### 2.3.1 ขอบเขตด้านฟังก์ชันการทำงานของระบบ (Functional Scope)

**2.3.1.1 ระบบแปลงไวยากรณ์คำสั่งเครือข่ายแบบไฟล์เดี่ยว (Single CLI / File Conversion)**

1. รองรับการแปลงคำสั่งแบบบรรทัดคำสั่งหรือไฟล์เดี่ยว ระหว่างระบบปฏิบัติการ Cisco IOS-XE
   และ Huawei VRP แบบสองทิศทาง (Bi-directional)
2. ประมวลผลด้วยกลไกลูกผสม (Hybrid Engine) ประกอบด้วย
   - **กลไกหลัก — Rule Engine** ทำหน้าที่แยกวิเคราะห์คำสั่ง (Parsing) แปลงเข้าสู่โครงสร้าง
     ข้อมูลกลาง (Intermediate Representation) และสร้างคำสั่งปลายทาง (Rendering)
   - **กลไกสำรอง — AI Fallback** เรียกใช้ Google Gemini API เฉพาะกรณีที่ Rule Engine
     ไม่พบกฎที่ตรงกันเท่านั้น
3. หมวดหมู่คำสั่งที่ Rule Engine รองรับ
   - คำสั่งกำหนดชื่ออุปกรณ์ (Hostname ↔ Sysname)
   - คำสั่งจัดการ VLAN และการตั้งชื่อ VLAN
   - คำสั่งจัดการ Interface (Description, IP Address, Subnet Mask/CIDR,
     Shutdown ↔ Undo Shutdown)
   - คำสั่งแปลงชื่อประเภท Interface (เช่น GigabitEthernet ↔ GE,
     TenGigabitEthernet ↔ XGE, Vlan ↔ Vlanif, Port-channel ↔ Eth-Trunk)
   - คำสั่งกำหนดรูปแบบพอร์ต (Access Port, Trunk Port, Trunk Allowed VLAN)
   - คำสั่งการจัดเส้นทางแบบคงที่ (Static Route)
   - คำสั่งการจัดเส้นทางแบบพลวัตพื้นฐาน (Basic OSPF: Process ID, Router-ID,
     Network, Area)
   - คำสั่งประเภท Comment, บรรทัดว่าง และคำสั่งออกจาก Configuration Mode
4. กรณีที่ไม่สามารถแปลงได้ หรือไม่ได้ตั้งค่า API Key หรือกลไก AI ทำงานล้มเหลว ระบบจะ
   กำกับคำสั่งเดิมไว้ในรูปของ Comment พร้อมป้ายแจ้งเตือน (Review Tag) เพื่อให้ผู้ดูแลระบบ
   ตรวจสอบด้วยตนเอง
5. แสดงผลลัพธ์การแปลงแบบเปรียบเทียบรายบรรทัด (Diff View) พร้อมระบุแหล่งที่มาของ
   การแปลงในแต่ละบรรทัด (`RULE` / `AI` / `UNMAPPED`) และหมายเหตุการแปลง
6. รองรับการคัดลอกผลลัพธ์ลง Clipboard และดาวน์โหลดเป็นไฟล์นามสกุล `.cfg`

**2.3.1.2 ระบบแปลงไฟล์แบบกลุ่ม (Batch File Conversion)**

1. รองรับการอัปโหลดหรือลากวางไฟล์ (Drag-and-Drop) นามสกุล `.cfg`, `.txt` และ `.conf`
   ครั้งละหลายไฟล์
2. สามารถกำหนด Vendor ต้นทางและปลายทางแยกรายไฟล์ได้
3. ประมวลผลการแปลงไฟล์ในคิวตามลำดับ พร้อมแสดงสถานะและแถบความคืบหน้า (Progress Bar)
4. สามารถดาวน์โหลดผลลัพธ์แยกรายไฟล์ หรือบีบอัดดาวน์โหลดรวมเป็นไฟล์ ZIP

**2.3.1.3 ระบบจัดการอุปกรณ์เครือข่าย (Device Inventory)**

1. บันทึกและจัดการข้อมูลอุปกรณ์เครือข่าย ได้แก่ Hostname, IP Address, Vendor,
   OS Version, SSH Port, Location และสถานะ
2. รองรับการค้นหาและกรองข้อมูลอุปกรณ์ตาม Hostname, IP Address, Location และ Vendor

**2.3.1.4 ระบบจำลองการส่งชุดคำสั่ง (Simulated Deployment)**

1. รองรับการเลือกอุปกรณ์เป้าหมายและปรับแก้ไขชุดคำสั่ง CLI ก่อนทำการส่ง
2. จำลองกระบวนการส่งคำสั่งไปยังอุปกรณ์ผ่าน API `/api/deploy/stream` และ
   Server-Sent Events (SSE)
3. แสดง Terminal Log แบบเรียลไทม์เป็นลำดับขั้นตอน (การเชื่อมต่อ, Authentication,
   เข้าสู่ Config Mode, การส่งคำสั่ง, Commit และปิด Session)
4. ค้นหา กรองระดับ Log (INFO, SUCCESS, WARNING, ERROR, COMMAND) ล้างข้อมูล
   และดาวน์โหลด Log ได้

**2.3.1.5 ระบบแสดงผลภาพรวมและประวัติการทำงาน (Dashboard & Audit History)**

1. แดชบอร์ดแสดงตัวเลขสรุปผล ได้แก่ จำนวนครั้งในการแปลง, จำนวนบรรทัดที่แปลงสำเร็จ,
   สัดส่วนการแปลงโดย Rule Engine เทียบกับ AI และจำนวนบรรทัดที่ถูกกำกับให้ตรวจสอบ
2. แสดงกราฟแนวโน้มการใช้งาน และสัดส่วนการแปลงแยกตาม Vendor
3. บันทึกประวัติการแปลงลงฐานข้อมูลถาวร สามารถดูเปรียบเทียบ Source/Target Diff
   คัดลอก Target Config และ Export ประวัติเป็นไฟล์ JSON

**2.3.1.6 ระบบตั้งค่าและส่วนติดต่อผู้ใช้ (System Settings & User Interface)**

1. ตรวจสอบสถานะการเชื่อมต่อ API Key ผ่าน Endpoint `/api/health`
2. รองรับการเปลี่ยนรูปแบบการแสดงผล (Light Theme / Dark Theme) โดยจดจำค่าผ่าน
   `localStorage`

> **หมายเหตุการแก้ไขขอบเขต** — มีการเปลี่ยนแปลงจากฉบับเดิมสามประการ
>
> 1. **ตัดระบบจำลองการทดสอบการเชื่อมต่อ (Simulated Ping / SSH Testing) ออกจากข้อ
>    2.3.1.3** เนื่องจากเป็นการจำลองด้วยตัวจับเวลาที่ไม่ได้สื่อสารกับอุปกรณ์จริง จึงไม่ให้
>    ข้อมูลที่นำไปใช้ประเมินผลในบทที่ 4 ได้ และย้ายไปอยู่ในข้อเสนอแนะเพื่อการพัฒนาต่อ
> 2. **ตัดการรองรับสองภาษา (ไทย/อังกฤษ) ออกจากข้อ 2.3.1.6** เนื่องจากใช้เวลาพัฒนาสูง
>    (ประมาณ 6–8 ชั่วโมง) แต่ไม่มีส่วนสนับสนุนวัตถุประสงค์ของโครงงานหรือผลการประเมิน
>    ในบทที่ 4 ทั้งนี้คงการสลับธีม Light/Dark ไว้ เนื่องจากใช้เวลาพัฒนาต่ำ
> 3. **ปรับเงื่อนไขการเรียกใช้ AI Fallback ให้ชัดเจน** ฉบับเดิมระบุเงื่อนไขไว้สองแบบที่
>    ขัดแย้งกัน ("สำหรับคำสั่งที่ไม่มีกฎรองรับ" และ "เมื่อมีการตั้งค่า API Key") หากระบบ
>    เรียกใช้ AI ทุกครั้งที่มี API Key กลไกดังกล่าวจะไม่ใช่ *กลไกสำรอง* และค่าสัดส่วนการแปลง
>    โดย Rule Engine ในข้อ 2.3.1.5 จะไม่มีความหมาย จึงกำหนดให้เรียกใช้ AI เฉพาะกรณีที่
>    Rule Engine ไม่พบกฎที่ตรงกันเท่านั้น

#### 2.3.2 ข้อจำกัดและเงื่อนไขของโครงงาน (Project Constraints & Limitations)

**2.3.2.1 การเชื่อมต่ออุปกรณ์จริง** ระบบไม่มีการเชื่อมต่อไปยังอุปกรณ์เครือข่ายทั้งที่เป็น
ฮาร์ดแวร์จริงและเครื่องเสมือน ไม่มีการเปิด SSH Session และไม่มีการส่งค่ากำหนดไปติดตั้งจริง
กระบวนการในข้อ 2.3.1.4 เป็นการจำลองผ่าน Timer และ SSE API เท่านั้น ยังไม่ได้ใช้ Library
จัดการเครือข่าย (เช่น Netmiko/Paramiko)

**2.3.2.2 การจัดเก็บข้อมูล (Data Persistence)** ข้อมูลอุปกรณ์ ประวัติการแปลง และสถิติของ
ระบบ จัดเก็บในฐานข้อมูล **SQLite** ซึ่งเป็นฐานข้อมูลถาวรแบบไฟล์เดียว ข้อมูลไม่สูญหายเมื่อ
Restart เซิร์ฟเวอร์

> **หมายเหตุการแก้ไข:** ฉบับเดิมระบุว่าใช้หน่วยความจำชั่วคราว (In-Memory Storage) และ
> ข้อมูลสูญหายเมื่อ Restart ข้อกำหนดดังกล่าวขัดแย้งกับข้อ 2.3.1.5 ที่ระบุว่าระบบมี
> "ประวัติการทำงาน (Audit History)" โดยตรง เพราะประวัติที่สูญหายเมื่อ Restart ไม่ถือเป็น
> ประวัติที่ตรวจสอบย้อนหลังได้ การเปลี่ยนมาใช้ SQLite ซึ่งเป็นส่วนหนึ่งของ Standard Library
> ของภาษา Python ใช้เวลาพัฒนาเพิ่มประมาณ 2 ชั่วโมง และขจัดข้อขัดแย้งนี้ทั้งหมด

**2.3.2.3 ขอบเขตสถาปัตยกรรมที่รองรับ** รองรับการแปลงเฉพาะคู่ระบบปฏิบัติการ
Cisco IOS-XE และ Huawei VRP เท่านั้น รองรับ OSPFv2 แบบ Process เดียวและ IPv4 เท่านั้น
คำสั่งประเภท Multi-Process OSPF, OSPFv3, BGP, IS-IS, ACL, QoS Policy และ VRF
อยู่นอกขอบเขต

**2.3.2.4 การไม่แปลงหมายเลขพอร์ต (Interface Numbering)** รูปแบบการนับหมายเลขพอร์ต
ของ Cisco และ Huawei สะท้อนโครงสร้างฮาร์ดแวร์ทางกายภาพ จึงไม่มีการแมปที่ถูกต้อง
สมบูรณ์ด้วยอัลกอริทึม ระบบจะแปลงเฉพาะส่วนที่เป็น *ประเภท* ของ Interface และคงส่วนที่เป็น
*ตัวเลข* ไว้ตามเดิม พร้อมแจ้งเตือนให้ตรวจสอบทุกบรรทัดที่หมายเลข Slot ไม่เป็นศูนย์

**2.3.2.5 ความแตกต่างของค่าเริ่มต้นสถานะพอร์ต** พอร์ต Switch ของ Cisco มีค่าเริ่มต้นเป็น
เปิดใช้งาน พอร์ต Router ของ Cisco มีค่าเริ่มต้นเป็นปิดใช้งาน ขณะที่พอร์ตของ Huawei
มีค่าเริ่มต้นเป็นเปิดใช้งาน กรณีที่ไฟล์ต้นทางไม่ระบุคำสั่งดังกล่าว ระบบจะไม่ระบุในไฟล์ผลลัพธ์
เช่นกัน โดยไม่พยายามอนุมานเจตนาของผู้ตั้งค่า

**2.3.2.6 ผลลัพธ์จาก AI เป็นเพียงคำแนะนำ** คำแนะนำจากกลไกสำรองจะถูกกำกับให้ตรวจสอบ
โดยมนุษย์ทุกครั้ง และไม่ถูกนำเสนอในฐานะผลการแปลงที่ผ่านการตรวจสอบแล้ว

**2.3.2.7 การตรวจสอบด้วยโปรแกรมจำลองเป็นการตรวจสอบบางส่วน** ความถูกต้องของผลลัพธ์
ตรวจสอบด้วย Huawei eNSP และ Cisco Packet Tracer เฉพาะไฟล์ตัวอย่างบางส่วนของชุดข้อมูล
ทดสอบ ไม่ใช่ทั้งชุด และไม่ได้ตรวจสอบบนอุปกรณ์ที่ใช้งานจริง

**2.3.2.8 ขอบเขตที่ยกไปเป็นข้อเสนอแนะเพื่อการพัฒนาต่อ** การส่งค่ากำหนดผ่าน SSH จริง
ด้วย Netmiko หรือ Paramiko, การรองรับคู่ผู้ผลิตเพิ่มเติม, การแปลงคำสั่ง ACL, QoS และ BGP,
ระบบสิทธิ์ผู้ใช้งานหลายระดับ และส่วนติดต่อผู้ใช้สองภาษา

### 2.4 รายละเอียดของทฤษฎีที่ใช้ในการจัดทำปริญญานิพนธ์

#### 2.4.1 สมมติฐานหรือข้อตกลงเบื้องต้นในการจัดทำโครงงานพิเศษ (Assumption of the Study)

**ความสมบูรณ์ของไฟล์กำหนดค่าต้นทาง (Source Configuration Validity)** ไฟล์กำหนดค่า
ที่นำเข้าสู่ระบบต้องอยู่ในรูปแบบไฟล์ข้อความธรรมดา (Plain Text File เช่น `.txt`, `.cfg`)
ที่ดึงมาจากอุปกรณ์ต้นทางที่สามารถทำงานได้จริง โดยผ่านการตรวจสอบไวยากรณ์คำสั่งแล้วว่า
ไม่มีข้อผิดพลาดรุนแรง (Syntax Error) หรือโครงสร้างไฟล์สูญหาย ระบบนี้เป็นเครื่องมือแปลง
ไม่ใช่เครื่องมือตรวจสอบไวยากรณ์ (Linter) จึงไม่ตรวจจับและไม่แก้ไขข้อผิดพลาดที่มีอยู่เดิม
ในไฟล์ต้นทาง

**ความสอดคล้องเชิงตรรกะของโปรโตคอลมาตรฐาน (Standard Protocol Functional
Equivalence)** ฟังก์ชันและโปรโตคอลเครือข่ายที่เป็นมาตรฐานสากล (เช่น VLAN, Static
Routing, OSPF) บนระบบปฏิบัติการของผู้ผลิตต่างรายมีหลักการทำงานเชิงตรรกะที่สอดคล้องกัน
แม้จะมีรูปแบบไวยากรณ์คำสั่งและสถาปัตยกรรมภาษาที่แตกต่างกัน

**ขอบเขตการจัดการคุณสมบัติเฉพาะตัว (Proprietary Features Limit)** สำหรับคำสั่งหรือ
คุณสมบัติที่เป็นฟีเจอร์เฉพาะของผู้ผลิตรายใดรายหนึ่งซึ่งไม่มีคำสั่งเทียบเคียงได้โดยตรงในอุปกรณ์
ปลายทาง ระบบจะแจ้งเตือน (Warning Message) และแปลงคำสั่งดังกล่าวเป็นข้อความอธิบาย
(Comment Header) ในไฟล์ผลลัพธ์ เพื่อให้ผู้ดูแลระบบนำไปพิจารณาปรับแต่งเพิ่มเติม

**สภาพแวดล้อมการติดตั้งใช้งาน (Target Operating Environment)** ไฟล์กำหนดค่าผลลัพธ์
จะถูกนำไปใช้กับอุปกรณ์ปลายทางที่มีเวอร์ชันของระบบปฏิบัติการ (Firmware/OS Version)
สอดคล้องกับฐานข้อมูลกฎการแปลง (Mapping Rules) ที่กำหนดไว้ในระบบ

**ระดับความรู้ของผู้ใช้งาน (Target User Competency)** ผู้ใช้งานระบบเป็นผู้ดูแลระบบหรือ
วิศวกรเครือข่ายที่มีความรู้ความเข้าใจพื้นฐานเกี่ยวกับระบบเครือข่ายคอมพิวเตอร์ และการใช้งาน
คำสั่งผ่านระบบบรรทัดคำสั่ง (CLI) เนื่องจากผลลัพธ์ที่ได้ต้องผ่านการตรวจสอบก่อนนำไปใช้

#### 2.4.2 คำจำกัดความ (Key Words)

**ระบบเครือข่ายแบบหลายผู้ผลิต (Multi-Vendor Network)** สภาพแวดล้อมของโครงสร้าง
พื้นฐานระบบเครือข่ายคอมพิวเตอร์ที่มีการติดตั้งและใช้งานอุปกรณ์เครือข่าย (เช่น Switch,
Router) จากผู้ผลิตหลากหลายแบรนด์ร่วมกันในระบบเดียว เช่น Cisco, Huawei, Juniper
หรือ Aruba

**ไฟล์กำหนดค่าอุปกรณ์เครือข่าย (Network Configuration File)** ไฟล์ข้อความที่บรรจุชุดคำสั่ง
ภาษา CLI ซึ่งบันทึกสภาวะ พารามิเตอร์การทำงาน นโยบายความปลอดภัย และโครงสร้าง
โปรโตคอลทั้งหมดของอุปกรณ์เครือข่ายนั้น

**ไวยากรณ์คำสั่งการตั้งค่า (Configuration Syntax)** รูปแบบ กฎเกณฑ์ ข้อกำหนดของคำสั่ง
และโครงสร้างภาษาที่ระบบปฏิบัติการเครือข่ายแต่ละผู้ผลิตกำหนดขึ้นเพื่อใช้ในการสื่อสารระหว่าง
ผู้ดูแลระบบกับอุปกรณ์ เช่น ไวยากรณ์ของ Cisco IOS-XE และ Huawei VRP

**การแปลงไวยากรณ์คำสั่ง (Syntax Mapping and Translation)** กระบวนการวิเคราะห์แยกแยะ
องค์ประกอบคำสั่ง (Parsing) การจับคู่ความสัมพันธ์ของพารามิเตอร์ (Parameter Mapping) และ
การสังเคราะห์คำสั่งใหม่ (Syntax Generation) จากภาษาผู้ผลิตต้นทางไปสู่ภาษาผู้ผลิตปลายทาง
โดยที่ผลลัพธ์การทำงานของระบบเครือข่ายยังคงเดิม

**ระบบปฏิบัติการเครือข่าย (Network Operating System — NOS)** ซอฟต์แวร์ระบบที่ทำหน้าที่
ควบคุมการทำงานของฮาร์ดแวร์อุปกรณ์เครือข่าย เช่น Cisco IOS-XE และ Huawei VRP
(Versatile Routing Platform)

**กลไกการแปลงแบบกฎ (Rule Engine)** ส่วนประกอบของระบบที่แปลงคำสั่งที่รู้จักตามกฎ
ที่เขียนไว้อย่างชัดเจน โดยให้ผลลัพธ์แน่นอนและทำซ้ำได้ (Deterministic)

**โครงสร้างข้อมูลกลาง (Intermediate Representation — IR)** โครงสร้างข้อมูลในหน่วยความจำ
ที่ไม่ขึ้นกับผู้ผลิตรายใด ใช้แทนเจตนาของการตั้งค่า (Configuration Intent) ทำหน้าที่แยก
ขั้นตอนการวิเคราะห์ไฟล์ต้นทางออกจากขั้นตอนการสร้างไฟล์ปลายทาง

**กลไกสำรองด้วยปัญญาประดิษฐ์ (AI Fallback)** ส่วนประกอบที่เรียกใช้แบบจำลองภาษาขนาด
ใหญ่ในขอบเขตจำกัด ทำงานเฉพาะเมื่อ Rule Engine ไม่พบกฎที่ตรงกับคำสั่งต้นทาง

**ความคงเดิมของการแปลงกลับ (Round-Trip Fidelity)** ระดับที่การแปลงจากผู้ผลิต A ไป B
แล้วแปลงกลับมาเป็น A ให้ผลลัพธ์ตรงกับไฟล์ต้นฉบับ

**บรรทัดที่มีนัยสำคัญ (Significant Line)** บรรทัดในไฟล์กำหนดค่าที่ไม่ใช่บรรทัดว่างและไม่ใช่
บรรทัด Comment ล้วน ใช้เป็นตัวส่วนในการคำนวณค่าความครอบคลุมของกฎ

**ข้อผิดพลาดจากมนุษย์ (Human Error)** ความผิดพลาดในการกำหนดค่าอุปกรณ์เครือข่าย

#### 2.4.4 เนื้อหา เหตุผล และทฤษฎีที่สำคัญ

**ก. โครงสร้างของไฟล์กำหนดค่าอุปกรณ์เครือข่าย**

อุปกรณ์เครือข่ายจัดเก็บค่ากำหนดการทำงานในรูปของเอกสารข้อความที่มีลำดับและมีโครงสร้าง
เชิงลำดับชั้น บรรทัดในระดับนอกสุดกำหนดค่าระดับระบบ ส่วนบรรทัดที่ย่อหน้าอยู่ภายใต้คำสั่งแม่
จะมีผลภายในบริบทนั้น ทั้ง IOS-XE และ VRP ใช้รูปแบบนี้ร่วมกัน

โครงสร้างดังกล่าวมีความสำคัญต่อการแปลง เพราะไฟล์กำหนดค่าไม่ใช่รายการคำสั่งที่เป็นอิสระ
ต่อกัน ความหมายของแต่ละบรรทัดขึ้นอยู่กับบล็อกที่บรรทัดนั้นอยู่ภายใน ตัวอย่างเช่น คำสั่ง
`description UPLINK` มีความหมายอย่างหนึ่งเมื่ออยู่ในบล็อก Interface และมีความหมาย
อีกอย่างหนึ่งเมื่ออยู่ในบล็อก VLAN

**ข. การเปรียบเทียบไวยากรณ์ระหว่าง Cisco IOS-XE และ Huawei VRP**

IOS-XE เข้าสู่โหมดกำหนดค่าด้วยคำสั่ง `configure terminal` ใช้เครื่องหมาย `!` เป็น Comment
ใช้คำนำหน้า `no` ในการยกเลิกคำสั่ง ปิดบล็อกด้วย `exit` หรือ `end` ระบุรายการ VLAN ด้วย
เครื่องหมายจุลภาคและขีดกลาง และระบุ Area ของ OSPF เป็นอาร์กิวเมนต์ท้ายบรรทัด `network`

VRP เข้าสู่โหมดกำหนดค่าด้วยคำสั่ง `system-view` ใช้เครื่องหมาย `#` เป็น Comment ใช้
คำนำหน้า `undo` ในการยกเลิกคำสั่ง ปิดบล็อกด้วย `quit` หรือ `return` ระบุรายการ VLAN
ด้วยการเว้นวรรคและคำว่า `to` และประกาศ Area ของ OSPF เป็นบล็อกแม่ที่บรรจุคำสั่ง
`network` ไว้ภายใน

**ค. การจัดประเภทความแตกต่างของไวยากรณ์ (ทฤษฎีหลักของโครงงาน)**

ความแตกต่างของไวยากรณ์แบ่งได้เป็นสามประเภท ซึ่งเป็นตัวกำหนดสถาปัตยกรรมของระบบ

| ประเภท | ลักษณะ | ตัวอย่าง | สัดส่วนโดยประมาณ |
|---|---|---|---|
| **Direct (D)** | แทนที่คำหรือบรรทัดแบบหนึ่งต่อหนึ่ง | `hostname` ↔ `sysname`, `no` ↔ `undo` | ~60% |
| **Transform (T)** | หนึ่งบรรทัดต่อหนึ่งบรรทัด แต่ต้องแปลงรูปแบบอาร์กิวเมนต์ | รายการ VLAN `10,20,30-35` ↔ `10 20 30 to 35` | ~25% |
| **Structural (S)** | โครงสร้างการซ้อนบล็อกหรือลำดับบรรทัดเปลี่ยนแปลง | OSPF | ~15% |

การมีอยู่ของกฎประเภท Structural คือ **ข้อค้นพบทางเทคนิคที่สำคัญที่สุดของโครงงานนี้**
พิจารณาตัวอย่างการแปลง OSPF ต่อไปนี้

```
! Cisco IOS-XE
router ospf 1
 router-id 1.1.1.1
 network 10.0.0.0 0.0.0.255 area 0
 network 172.16.0.0 0.0.0.255 area 1
```

```
# Huawei VRP
ospf 1 router-id 1.1.1.1
 area 0.0.0.0
  network 10.0.0.0 0.0.0.255
 area 0.0.0.1
  network 172.16.0.0 0.0.0.255
```

มีการเปลี่ยนแปลงเกิดขึ้นสามอย่างพร้อมกัน คือ (1) `router-id` ถูกเลื่อนขึ้นไปอยู่บนบรรทัด
ประกาศ Process (2) Area กลายเป็นบล็อกแม่ ทำให้ต้องจัดกลุ่มคำสั่ง `network` ตาม Area
ซึ่งหมายความว่าระบบไม่สามารถสร้างผลลัพธ์ได้จนกว่าจะอ่านบล็อก `router ospf` ทั้งบล็อกจนจบ
และ (3) หมายเลข Area แปลงจากเลขจำนวนเต็มเป็นรูปแบบเลขฐานสิบแบบมีจุด (Cisco
`area 1` ↔ Huawei `area 0.0.0.1`)

**สถาปัตยกรรมแบบแทนที่รายบรรทัด (Line-by-Line Substitution) ซึ่งเป็นแนวทางที่เข้าใจ
ได้ง่ายที่สุดในเบื้องต้น ไม่สามารถแสดงการแปลงประเภทนี้ได้** ข้อจำกัดนี้เป็นเหตุผลที่โครงงาน
ต้องใช้โครงสร้างข้อมูลกลาง

**ง. ทฤษฎีการแปลภาษาและการประยุกต์ใช้**

สถาปัตยกรรมที่โครงงานนี้เลือกใช้เป็นไปตามโครงสร้างของตัวแปลภาษาแบบต้นทางสู่ต้นทาง
(Source-to-Source Translator) ตามที่ปรากฏในทฤษฎีการสร้างตัวแปลโปรแกรม กล่าวคือ
มีส่วนหน้า (Front End) ที่วิเคราะห์โครงสร้างของข้อมูลเข้า มีโครงสร้างข้อมูลกลางที่ไม่ขึ้นกับ
รูปแบบทั้งของข้อมูลเข้าและข้อมูลออก และมีส่วนหลัง (Back End) ที่สร้างข้อมูลออก

| ขั้นตอนตามทฤษฎีตัวแปลโปรแกรม | ส่วนประกอบของระบบ NetMigrate |
|---|---|
| การวิเคราะห์คำและวิเคราะห์ไวยากรณ์ | ตัวแยกวิเคราะห์ไฟล์แบบรู้จักบล็อก (Block-Aware Parser) |
| โครงสร้างข้อมูลกลาง | แบบจำลองค่ากำหนดที่ไม่ขึ้นกับผู้ผลิต (IR) |
| การสร้างรหัสเป้าหมาย | ตัวสร้างไฟล์กำหนดค่าแยกตามผู้ผลิต (Renderer) |

ประโยชน์ของสถาปัตยกรรมนี้เหมือนกับในการสร้างตัวแปลโปรแกรม กล่าวคือ การเพิ่มผู้ผลิต
รายใหม่ต้องพัฒนาเพียง Parser หนึ่งชุดและ Renderer หนึ่งชุด แทนที่จะต้องเขียนกฎการแปลง
สำหรับทุกคู่ผู้ผลิตที่มีอยู่ กล่าวคือใช้ส่วนประกอบจำนวน *n* + *n* ชุด แทนการแมป *n*²
คู่ความสัมพันธ์ คุณสมบัตินี้ทำให้ข้อเสนอแนะเรื่องการรองรับผู้ผลิตเพิ่มเติมในอนาคต
มีความเป็นไปได้จริงในเชิงเทคนิค ไม่ใช่เพียงการคาดการณ์

**จ. ตำแหน่งทางวิชาการของโครงงาน**

คำถามที่คณะกรรมการมีแนวโน้มตั้งขึ้นคือ เหตุใดจึงต้องพัฒนาระบบแปลงไฟล์ข้อความ
ในขณะที่มาตรฐาน NETCONF/YANG และ OpenConfig มีอยู่แล้ว คำตอบมีสามประการ

*ประการที่หนึ่ง — อุปกรณ์ที่ติดตั้งใช้งานอยู่แล้ว* การกำหนดค่าด้วยแบบจำลองข้อมูลกำหนดให้
ตัวอุปกรณ์ต้องรองรับมาตรฐาน องค์กรที่กำลังย้ายออกจากอุปกรณ์รุ่นเก่าจำเป็นต้องทำงานกับ
ไฟล์กำหนดค่าที่เป็นข้อความซึ่งอุปกรณ์เหล่านั้นมีอยู่จริง นอกจากนี้ การแสดงค่ากำหนดของ
ระบบที่ใช้งานอยู่ให้อยู่ในรูปแบบ OpenConfig ยังเป็นงานที่ต้องใช้ความพยายามในตัวเอง
และไม่ได้ให้ผลลัพธ์ที่วิศวกรผู้ทำการย้ายระบบต้องการโดยตรง ซึ่งก็คือไฟล์กำหนดค่าที่ใช้งาน
ได้สำหรับอุปกรณ์ตัวใหม่

*ประการที่สอง — ความสอดคล้องกับลักษณะงาน* Batfish แปลงไฟล์กำหนดค่าจากหลายผู้ผลิต
เพื่อ *วิเคราะห์* ไม่ได้สร้างไฟล์กำหนดค่าสำหรับผู้ผลิตรายอื่น ผลลัพธ์ของโครงงานนี้คือไฟล์
กำหนดค่าของผู้ผลิตปลายทางโดยตรง

*ประการที่สาม — ปัญหาความโปร่งใสของความครอบคลุมยังไม่ได้รับการแก้ไข* เครื่องมือที่กล่าว
มาข้างต้นไม่มีเครื่องมือใดที่รวมการแปลงแบบกำหนดผลลัพธ์แน่นอนเข้ากับการรายงานอย่าง
ชัดเจนและวัดผลได้ว่าบรรทัดใดอยู่นอกเส้นทางการแปลงแบบกำหนดผลลัพธ์แน่นอน การรวม
องค์ประกอบสี่อย่าง ได้แก่ Rule Engine, กลไกสำรองเชิงความน่าจะเป็นที่มีขอบเขตจำกัด,
การระบุแหล่งที่มาของการแปลงในระดับรายบรรทัด และการวัดค่าความครอบคลุมเชิงปริมาณ
คือส่วนที่โครงงานนี้มุ่งนำเสนอ

โครงงานนี้จึงวางตำแหน่งตนเองในฐานะเครื่องมือช่วยการย้ายระบบที่ใช้งานได้จริงและระบุ
ข้อจำกัดของตนเองอย่างวัดผลได้ ไม่ใช่สิ่งที่มาแทนที่การบริหารจัดการเครือข่ายด้วยแบบจำลอง
ข้อมูล

**ฉ. แบบจำลองภาษาขนาดใหญ่สำหรับการแปลงคำสั่ง และข้อจำกัดที่ต้องคำนึงถึง**

แบบจำลองภาษาขนาดใหญ่แสดงความสามารถในการแปลงรหัสต้นฉบับข้ามภาษาและการสร้าง
ข้อความเชิงเทคนิคที่มีโครงสร้าง ข้อจำกัดที่เกี่ยวข้องกับโครงงานนี้คือ ผลลัพธ์ของแบบจำลอง
เป็นเชิงความน่าจะเป็น กล่าวคือ ผลลัพธ์ที่อ่านลื่นไหล ดูสมเหตุสมผล และถูกต้องตามไวยากรณ์
อาจผิดพลาดในเชิงความหมายได้ และตัวแบบจำลองไม่ได้ให้สัญญาณภายในที่เชื่อถือได้ในการ
แยกแยะสองกรณีนี้ออกจากกัน

ข้อจำกัดดังกล่าวนำไปสู่การตัดสินใจออกแบบสองประการ

1. **ค่าความมั่นใจที่แบบจำลองรายงานด้วยตนเอง (Self-Reported Confidence) ไม่ถือเป็น
   ตัวชี้วัดความน่าเชื่อถือที่ผ่านการตรวจสอบความสมเหตุสมผล** ค่าดังกล่าวแสดงบนส่วนติดต่อ
   ผู้ใช้เพื่อเป็นข้อมูลประกอบเท่านั้น และถูกตัดออกจากตัวชี้วัดการประเมินผลในข้อ 2.6
   อย่างชัดเจน
2. **ผลลัพธ์ที่ได้จากแบบจำลองไม่ถูกนำไปใช้เป็นคำสั่งในไฟล์ผลลัพธ์โดยตรง** แต่จะถูกกำกับ
   ไว้ในรูป Comment พร้อมป้ายให้ตรวจสอบ

การนำผลลัพธ์ของแบบจำลองที่ยังไม่ผ่านการตรวจสอบไปใช้กับค่ากำหนดของเครือข่ายที่ให้บริการ
จริง เป็นสิ่งที่ไม่อาจยอมรับได้ในทางวิชาชีพ และการออกแบบระบบเสมือนว่าการกระทำดังกล่าว
เป็นที่ยอมรับได้ จะทำให้ผลของโครงงานอ่อนแอลงมากกว่าจะแข็งแรงขึ้น

### 2.6 วิธีดำเนินการจัดทำโครงงานพิเศษ

การจัดทำโครงงานพิเศษระบบ NetMigrate ดำเนินการตามวงจรชีวิตการพัฒนาระบบ (System
Development Life Cycle: SDLC) แบบพัฒนาเพิ่มทีละส่วน (Incremental Development)
ร่วมกับการกำหนดจุดตรึงขอบเขต (Scope Freeze) สองจุด เนื่องจากระยะเวลาพัฒนาที่มีอยู่
ไม่เพียงพอต่อการดำเนินวงรอบการพัฒนาแบบวนซ้ำหลายรอบให้ครบถ้วน

#### 2.6.1 ขั้นตอนการดำเนินงาน

**1. การศึกษาและรวบรวมข้อมูล** ศึกษาสถาปัตยกรรมไวยากรณ์คำสั่งระหว่างระบบปฏิบัติการ
Cisco IOS-XE และ Huawei VRP ในหมวดคำสั่งที่กำหนดขอบเขตไว้ (Hostname, VLAN,
Interface, Switchport, Static Route, OSPF) จัดทำตารางกฎการแปลงพร้อมจัดประเภท D/T/S
ตามข้อ 2.4.4 (ค) รวมถึงศึกษาวิธีการเชื่อมต่อ Google Gemini API

**2. การวิเคราะห์และออกแบบระบบ** ออกแบบสถาปัตยกรรมระบบสามชั้น ออกแบบโครงสร้าง
ข้อมูลกลาง (IR) ออกแบบอัลกอริทึมของ Rule Engine ออกแบบ Prompt สำหรับกลไกสำรอง
ออกแบบโครงสร้างฐานข้อมูล SQLite และออกแบบส่วนติดต่อผู้ใช้

**3. การพัฒนาระบบ (System Development)**
- **ระยะที่ 1 — กลไกการแปลงหลัก** พัฒนา Block-Aware Parser, โครงสร้างข้อมูลกลาง
  และ Rule Engine ทั้งสองทิศทาง พร้อมชุดทดสอบระดับหน่วย (Unit Test) รายกฎ
- **ระยะที่ 2 — ฟังก์ชันสนับสนุน** พัฒนากลไกสำรองด้วย AI, การแปลงแบบกลุ่ม,
  ฐานข้อมูล, แดชบอร์ด, คลังอุปกรณ์ และระบบจำลองการส่งชุดคำสั่งผ่าน SSE
- **ระยะที่ 3 — การประเมินผลและจัดทำเอกสาร** จัดทำชุดข้อมูลทดสอบ เก็บค่าตัวชี้วัด
  ตรวจสอบผลลัพธ์บนโปรแกรมจำลอง และเขียนรายงาน

การพัฒนา Rule Engine ใช้แนวทางการพัฒนาที่ขับเคลื่อนด้วยการทดสอบ (Test-Driven
Development) โดยเขียนชุดทดสอบระดับหน่วยของแต่ละกฎก่อนการเขียนโปรแกรม ซึ่งมี
ประโยชน์สองประการคือควบคุมข้อบกพร่อง และสร้างหลักฐานเชิงประจักษ์สำหรับใช้ในบทที่ 4

**4. การทดสอบและประเมินผลระบบ** รายละเอียดตามข้อ 2.6.3

**5. การจัดทำเอกสารและสรุปผล** รวบรวมผลการทดสอบ วิเคราะห์ผล และจัดทำรายงาน
ปริญญานิพนธ์ฉบับสมบูรณ์

เนื่องจากโครงงานนี้ดำเนินการโดยนักศึกษาสองคน จึงแบ่งภาระงานตามชั้นของสถาปัตยกรรม

แนวทางหลักในการตอบข้อวิจารณ์ที่ว่าความถูกต้องของการแปลงเป็นเพียงการกล่าวอ้าง

**จ. ข้อจำกัดที่อาจกระทบความน่าเชื่อถือของผลการประเมิน (Threats to Validity)**

   ที่ใช้งานจริง
2. การตรวจสอบด้วยโปรแกรมจำลองยืนยันได้เพียงว่าไวยากรณ์ถูกยอมรับ ไม่ได้ยืนยันว่า
   พฤติกรรมของเครือข่ายถูกต้อง
3. เกณฑ์พื้นฐานจากการทำด้วยตนเองวัดโดยผู้พัฒนาระบบเอง
4. ความถูกต้องของคำแนะนำจาก AI ประเมินโดยผู้จัดทำ ไม่ใช่คณะผู้เชี่ยวชาญอิสระ

### 2.9 ผลที่คาดว่าจะได้รับ

#### 2.9.1 เชิงปริมาณ (Quantitative Benefits)

ผลที่คาดว่าจะได้รับเชิงปริมาณระบุในรูปของสมมติฐานที่ทดสอบได้ พร้อมนิยามการวัดตามข้อ
2.6.3 (ข)

| สมมติฐาน | ข้อความสมมติฐาน | ค่าเป้าหมาย |
|---|---|---|
| H1 | ความครอบคลุมของกฎบนชุดข้อมูลทดสอบที่อยู่ในขอบเขต | ไม่ต่ำกว่า 85% ของบรรทัดที่มีนัยสำคัญ |
| H2 | ความคงเดิมของการแปลงกลับสำหรับกฎประเภท D และ T | ไม่ต่ำกว่า 95% |
| H3 | ไฟล์ผลลัพธ์นำเข้าโปรแกรมจำลองได้โดยไม่เกิด Syntax Error | ไม่ต่ำกว่า 90% ของไฟล์ตัวอย่างที่ตรวจสอบ |
| H4 | ระยะเวลาการแปลงเทียบกับเกณฑ์พื้นฐานจากการทำด้วยตนเอง | ลดลงไม่ต่ำกว่า 80% |
| H5 | ความถูกต้องของคำแนะนำจากกลไกสำรองด้วย AI | รายงานผลตามที่วัดได้ ไม่กำหนดค่าเป้าหมาย |

สมมติฐาน H5 ไม่กำหนดค่าเป้าหมายโดยเจตนา วัตถุประสงค์ของการวัดคือการระบุลักษณะ
ความน่าเชื่อถือของกลไกสำรอง ค่าที่วัดได้ต่ำถือเป็นผลการวิจัยที่ใช้ได้และเป็นหลักฐานสนับสนุน
การตัดสินใจออกแบบให้ *กำกับให้ตรวจสอบ* แทนการ *นำไปใช้โดยอัตโนมัติ* ตามข้อ 2.4.4 (ฉ)

> **หมายเหตุการแก้ไขที่สำคัญ** — ฉบับเดิมระบุผลที่คาดว่าจะได้รับไว้สองข้อซึ่งควรปรับ
>
> 1. **"ลดอัตราข้อผิดพลาดด้านไวยากรณ์เหลือ 0% ในหมวดคำสั่งที่ Rule Engine รองรับ"**
>    ข้อความนี้เป็นการให้เหตุผลแบบวนกลับ (Circular Reasoning) กล่าวคือ ระบบย่อมให้ผลลัพธ์
>    ถูกต้องสำหรับกรณีที่ผู้พัฒนาเขียนกฎรองรับไว้เองโดยนิยาม การอ้างค่า 0% จึงไม่ได้ให้
>    ข้อมูลใดเพิ่ม และเป็นประเด็นที่คณะกรรมการตรวจพบได้ทันที จึงแทนที่ด้วย H1 (ความ
>    ครอบคลุม) และ H2 (ความคงเดิมของการแปลงกลับ) ซึ่งวัดได้จริงและมีความหมาย
> 2. **"เร็วกว่าการทำด้วยตนเองมากกว่า 80%"** ฉบับเดิมไม่ได้ระบุว่าเปรียบเทียบกับเกณฑ์
>    พื้นฐานใดและวัดอย่างไร จึงคงค่าเป้าหมายไว้ในรูป H4 แต่เพิ่มนิยามการวัดและวิธีการ
>    สร้างเกณฑ์พื้นฐานไว้ในข้อ 2.6.3 (ค)

นอกจากนี้ ระบบรองรับการแปลงไฟล์แบบกลุ่ม (Batch Conversion) ได้คราวละหลายไฟล์
ซึ่งช่วยลดเวลาเตรียมการสำหรับโครงการย้ายระบบเครือข่ายขนาดใหญ่

#### 2.9.2 เชิงคุณภาพ (Qualitative Benefits)

**เพิ่มความต่อเนื่องของระบบเครือข่าย (Business Continuity)** ลดความเสี่ยงจากภาวะระบบ
เครือข่ายหยุดชะงัก (Downtime) ที่เกิดจากการตั้งค่าผิดพลาดเมื่อต้องย้ายระบบข้ามผู้ผลิต

**ลดภาระงานและเพิ่มประสิทธิภาพการทำงาน** วิศวกรและผู้ดูแลระบบเครือข่ายไม่ต้องจดจำ
ไวยากรณ์คำสั่งของทุกผู้ผลิต สามารถบริหารจัดการอุปกรณ์แบบ Multi-Vendor ได้สะดวกยิ่งขึ้น

**เพิ่มความโปร่งใสและความสามารถในการตรวจสอบ** ผู้ดูแลระบบทราบแหล่งที่มาของการแปลง
ในระดับรายบรรทัด และทราบว่าบรรทัดใดต้องตรวจสอบด้วยตนเองก่อนนำไปใช้ ซึ่งเป็น
คุณสมบัติที่จำเป็นต่อการนำระบบอัตโนมัติไปใช้กับเครือข่ายที่ให้บริการจริง

**ได้สถาปัตยกรรมที่ขยายต่อได้** โครงสร้างแบบ Parser → IR → Renderer ทำให้การเพิ่ม
ผู้ผลิตรายใหม่ในอนาคตต้องพัฒนาเพียงส่วนประกอบสองชิ้นต่อผู้ผลิต แทนการเขียนกฎสำหรับ
ทุกคู่ความสัมพันธ์

**เป็นต้นแบบระบบบริหารจัดการเครือข่ายอัตโนมัติ** ได้ระบบซอฟต์แวร์ต้นแบบ (Prototype)
ที่สามารถนำไปพัฒนาต่อยอดเชื่อมต่อกับอุปกรณ์จริงผ่าน SSH ในอนาคตได้
